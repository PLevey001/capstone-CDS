# Optional local AI

AI case brief generates and saves a versioned overall JSON assessment from computed saved-result facts. It separates overall summary, observations, tentative inferences/hypotheses (with reasoning, alternatives and limitations), and recommended review/questions. All four generated categories are unverified, and inferences are not evidence. No inference is required when the supplied observations do not support one. Learn with AI answers questions and follow-ups in two explicit modes:

- **Explain concepts** sends local glossary text and the conversation, with no case facts or case name. It gives general education, not observations about a case. Do not paste evidence into questions if you want this mode to remain free of case information.
- **Ask about this case** builds fresh facts from the selected case's saved database results. Source references open the exact saved run and, when available, artifact. Client-supplied facts are rejected. Conversation and earlier answers are untrusted context, never evidence. An optional saved brief is selected explicitly in case mode; its historical F snapshot and source/run links are pinned to that brief after current-input checks. `A-...` references identify prior unverified assessment items; `F...` references identify server-computed facts. The prior assessment is never promoted to evidence or system instructions. Concept mode cannot select a brief.

Every generated statement is **unverified**. Valid references and matching number tokens do not establish meaning, intent, identity, guilt, or accuracy. For example, a statement about deliberate destruction can pass mechanical checks while citing an inventory count. No semantic verification is claimed. Read the reference text, saved run and coverage yourself.

Concept answers show the cited reviewed local text beside the generated explanation by default, using the reference snapshot returned with that answer. SHA-256 notes distinguish integrity relative to a reference from trust in that reference or software safety. Registry notes distinguish a key's last-write time from an individual value's change time. The model can still contradict these notes; visible references and warnings do not establish answer quality. Unsupported concept questions receive a reference-limitation message, without assuming the question was case-specific.

## Shared runtime guidance

The [v0.2 AI guidance pack](ai-guidance/README.md) specifies shared forensic rules, brief/chat behavior, authored examples and human evaluation. A compact subset in six fixed `cds/prompts/*.txt` files is loaded at process startup by `cds/prompt_guidance.py`. Both brief and chat paths send common plus appropriate mode instructions as SYSTEM content; [the exact compositions and checksum definition](ai-guidance/README.md#what-actually-runs) cover case, concept and selected-prior-assessment modes. Missing or blank files fail clearly. Restart CDS after edits. Both paths return full-system `prompt_sha256`, `prompt_version` and `guidance_version`; saved/downloaded briefs preserve them. Historical documents are not rewritten. Full docs and examples are not sent to the model, and no weights have been trained. These are application model prompts, distinct from developer `AGENTS.md` instructions. Model-independent rules do not imply arbitrary provider support or reliable behavior from every model.

## Setup

Install Ollama using its [official installation instructions](https://ollama.com/download). Record `ollama --version` when validating a deployment. CDS uses Ollama's [chat API](https://docs.ollama.com/api/chat) with JSON schema output and requires `done: true`, `done_reason: "stop"`, and the configured model in a complete reply. It does not retry arbitrary HTTP 400 responses or fall back to a cloud service.

Run Ollama bound only to loopback, with cloud features disabled:

```bash
OLLAMA_HOST=127.0.0.1:11434 OLLAMA_NO_CLOUD=1 ollama serve
```

In a separate terminal, download the default model once (installation requires internet access):

```bash
OLLAMA_HOST=127.0.0.1:11434 ollama pull llama3.2:3b
```

If Ollama already runs as a service, set these environment variables for that service and restart it instead of launching a second instance. See [Ollama configuration and disabling cloud features](https://docs.ollama.com/faq). CDS cannot enforce how a separately administered Ollama service is configured.

After the initial dependency installation and frontend build, start with `python3 scripts/run.py`. It works from standard-library Python and execs the project virtual environment. Optionally copy `.env.example` to repo-root `.env` (already ignored). Supported syntax is plain `KEY=value`, blank/comment lines, and an optional matching single/double quote wrapper. There is no shell sourcing, command execution, interpolation, escape processing, `export` prefix, or inline-comment syntax. Shell variables win, including empty values. Unknown/duplicate keys and malformed syntax report a line number without echoing the value. Supported keys are `CDS_DATA_DIR`, `CDS_WORKERS`, `CDS_MAX_UPLOAD_BYTES`, `CDS_MAX_ARTIFACTS`, `CDS_TOOL_TIMEOUT`, `CDS_AI_URL`, `CDS_AI_MODEL`, `CDS_AI_TIMEOUT`, `CDS_AI_CONTEXT`, and `CDS_AI_SERVICE`. Relative data directories resolve from the repo root when launched this way.

`CDS_AI_SERVICE` is unset by default. If explicitly configured (for example `cds-ollama.service`), the launcher validates one user `.service` name and runs only `systemctl --user start <unit>`, with a ten-second timeout. After a successful start, it prints a pending message and allows up to ten additional seconds for API readiness and model discovery. Connection failures are retried within that deadline because starting the service can precede its HTTP listener. A ready API with a missing model reports installation guidance immediately. Without a successful service start, discovery uses its usual three-second limit. Checks use `/api/tags` and `/api/show`, without proxies or inference. The launcher does not assume systemd on other platforms, start Ollama directly, install anything, pull a model, or stop an external runtime at exit. Failure prints a next step and the app still starts. The startup banner shows the app URL, configured model and availability; UI status remains authoritative. No model is silently downloaded or substituted.

Start CDS normally. The AI panels show model availability and offer **Check again**. No model is necessary for the fact sheet, local glossary, inventory, timeline, records, extraction, or export. CPU generation may take a minute or more; latency and quality depend on hardware, model and runtime version. Real-model quality/latency must be evaluated separately from scripted tests.

| CDS environment setting | Default | Meaning |
| --- | --- | --- |
| `CDS_AI_URL` | `http://127.0.0.1:11434` | Plain loopback HTTP only; no credentials, paths or queries. `localhost` is normalized to `127.0.0.1` before connecting. IPv6 `http://[::1]:11434` is also accepted. |
| `CDS_AI_MODEL` | `llama3.2:3b` | An installed local GGUF model advertising completion support through `/api/show`. Cloud names or remote metadata are refused. |
| `CDS_AI_TIMEOUT` | `180` | Overall discovery plus generation deadline in seconds, including response reads. |
| `CDS_AI_CONTEXT` | `8192` | Context tokens, configurable from 8192 through 32768. Lower settings are rejected at startup because fixed instructions and schema need room. Larger settings use more memory; long conversations or large cases can still exceed the budget. |

Use a model/runtime supporting the documented schema chat contract. There is no claim of compatibility with every Ollama version or custom model template. Model discovery uses [tags](https://docs.ollama.com/api/tags) and [show](https://docs.ollama.com/api-reference/show-model-details). No runtime is required by automated tests. Do not expose either service to a network, configure reverse proxies to it, or substitute a remotely forwarded loopback endpoint. The client makes direct connections without system proxies and rejects redirects.

## Lifetime, boundaries and limits

Case questions are rejected before model generation if the bounded context would omit any entire evidence source. Review the full computed fact sheet, clear history, shorten the question, or deselect the brief. Below 32768, `CDS_AI_CONTEXT` can be increased up to 32768 only if the installed model supports it, without guaranteeing that a request fits. At 32768, do not increase it: CDS's conservative request byte budget is distinct from the model's token capacity. This prevents a partial source set being used for a whole-case question; it does not verify generated meaning or guarantee that all details fit. Concept questions remain available. Assessment generation also rejects whole-source omissions before calling the model; omitted details within represented sources are disclosed with counts and IDs.

Chat lives in browser memory only and clears on reload, tab exit, case/mode/name changes, or observed source revisions. Clear conversation also discards pending browser replies. The server may still be finishing an interrupted request; brief and chat share one generation slot and another request receives 409 until that work ends. No raw conversation or generated chat answer is written to the CDS database or audit. Successful brief generation stores the full immutable JSON document and a transactional audit entry containing version/model/count/digest metadata. Failed or incomplete generation does not save a version. Ollama has its own process memory and service logging configuration, outside CDS's persistence controls.

The model receives no raw evidence files and has no tools, web access, command execution, or evidence mutation capability. CDS does not make external model calls or fetch educational references during generation. Glossary links are static local content and open only when clicked. Evidence names, record summaries and conversation text can contain hostile instructions: fixed system instructions and reference validation reduce exposure but do not make prompt injection impossible.

Input is bounded in UTF-8 bytes, conservatively allowing one byte per input token after reserving 900 output tokens for chat or 1800 for briefs and 1024 tokens for chat-template overhead. The input budget includes system instructions, glossary/facts, history, question and schema. This is a conservative budgeting rule, not an exact tokenizer for every custom model. The full computed fact sheet remains accessible in Case brief without AI. Model selection preserves case and general scope, then source identities together with their saved coverage scopes, parser details and warnings, then every F reference cited by a selected assessment, then optional details in stable order. Unknown required IDs or required references that cannot fit fail with 422 before transport; they cannot displace mandatory source coverage. A source's identity and coverage notes are indivisible: if they cannot fit, that source and its aggregates are omitted from model input. Source and optional-detail passes stop at the first item that exceeds the remaining budget or 160 facts; required references must fit as a group. The existing 512-byte omission-notice reserve remains. Returned context metadata/UI state counts omitted facts and sources, including sources with omitted details. Selection can change with the length of a follow-up; citations use the references returned with that answer. The brief audit records sent and omitted fact counts alongside the full-input digest. Saved `facts` contain the complete computed snapshot; `model_facts` contain the original ID/text pairs represented in model input, even when that input uses the lossless dictionary below. The full computed snapshot is an aggregate view, not every raw evidence record. `context` lists omitted fact/source IDs and counts. `provenance.aggregate_omissions` separately counts deleted entries, host groups and event groups omitted by aggregation caps. Source snapshots retain exact source names, full SHA-256 where available, coverage and saved run references; itemized deleted entries retain exact paths and artifact IDs.

Brief and chat use one deterministic model-view renderer. For `source_scope` facts only, it verifies the exact generated prefix `Saved scope/detail for "<clean(source_name)>": ` and a unique source identity matching the source ID, run ID and original name. Only exactly equal remaining suffixes are shared; there is no semantic merging, Unicode normalization or shortening. The dictionary has `scope_texts` (S label to literal suffix), `sources` (source F ID to the same cleaned name used in the original prefix), and `facts` entries `{id, source, scope}`. Reconstruct each entry as `'Saved scope/detail for "' + sources[source] + '": ' + scope_texts[scope]`. Separate source F IDs distinguish duplicate or identically cleaned names. JSON escaping protects dictionary boundaries; strings remain untrusted data. Other facts and unrecognized historical wording retain ordinary F lines. Dictionary encoding is used only if it reduces JSON-escaped UTF-8 request bytes, including its explanation. `context.fact_representation` reports `facts.scope-dictionary.v1` or `facts.lines.v1` for the actual selected input. Counts still refer to original F facts, not dictionary entries. Canonical facts, digests, numeric validation, response/UI supporting text, and previously saved/downloaded documents retain their original text and source/run links. This is byte reduction, not a claim about actual token counts.

Chat requests are capped at 16 KiB before parsing (including chunked requests), eight prior history messages in complete user/assistant pairs, and 2000 UTF-8 bytes per message. These are simultaneous upper bounds, not a promise that four full-length prior turns plus a question fit. JSON field names, punctuation and escaping also count toward the body cap; model context additionally includes the fixed instructions and references. A request can satisfy each field limit yet exceed the body or context limit and receive 422. Shorten the question or clear the conversation when needed. Clients cannot submit system messages or extra fact fields. History is rejected when over budget, never silently trimmed. Model HTTP requests/replies are capped at 128/256 KiB; generated JSON content at 16 KiB; displayed chat prose at 2000 UTF-8 bytes. For saved assessments, any malformed or overlong item, unknown/mixed reference, numeric mismatch or overflow rejects the entire document; no partial or silently truncated assessment is saved. Summary/observations/inferences/review lists allow at most 3/6/3/4 items. Summary must be nonempty; inferences may be empty. Each inference requires nonempty reasoning, one to three alternatives, and one to three limitations. Every prose field is at most 400 characters, and every item cites one to twelve unique supplied F IDs. Chat statements over 400 characters are withheld whole, as are malformed statements, any unknown/mixed references, numeric mismatches and overflow; its omission counts include every withheld item. These checks can reject valid wording and can accept false wording.

The generation grammar deliberately has no string `maxLength`: constraining generation at a character boundary can force malformed sentence endings. Server validation still enforces the 400-character limit without truncating prose, and bounded output caps remain (900 for chat, 1800 for briefs). Brief generation grammar requests at most three citations per item to discourage padding; validation retains the older maximum of twelve for compatibility. Prompts request complete, self-contained sentences around 200 characters, minimal relevant citations and precise descriptions of measured scope. Literal inline F/G/A references must also appear in that item's structured references; unknown or unlisted inline IDs fail the checks. For selected-brief chat, numeric comparison reads only assessment prose, excluding metadata and reference-label digits. Trailing commas, semicolons or colons are rejected as dangling punctuation. These are narrow mechanical checks: they do not establish that a sentence is complete, its citations support it, or its meaning is correct. Human review must still flag fragments, overstated scope and unsupported interpretations.

Case follow-ups require the previous fact digest. Canonical hashing includes every fact's text and stable provenance, including case/source/run/artifact identifiers and current-job identity/status. Responses return the digest and provenance snapshot. A case change during generation or a stale/cross-case digest returns 409. Saved brief references always use the historical snapshot, even after current facts change or fail to refresh. The UI rejects late results for cleared/replaced chat sessions. Selected-brief chat sends all assessment categories, alternatives and limitations and requires their underlying F references to fit with the selected historical fact snapshot, history, question and schema; otherwise it returns 422 without sending anything. It never silently drops assessment uncertainty to fit. Only repeated per-item `verification` and `category` display fields are removed from model-bound items: the enclosing boundary declares all A items unverified and A IDs encode their category. Response/UI items retain both fields. All hypotheses, reasoning, alternatives, limitations, cited F IDs and the complete `original_context_limits` object remain in model input.

An unmeasured inventory is reported as unavailable, not zero. Saved results may predate the current job. Source-specific coverage scopes, parser details and warnings remain visible even for completed analyses; missing data does not establish absence. Browser host totals exclude truncated, missing and unclassifiable URLs and disclose those counts. File time extrema include representable pre-1970 values and exclude unavailable zero or out-of-range values before aggregation. Itemized deleted entries and top host/event lists retain their existing caps. Full-sheet aggregation still visits all sources and scans saved artifact/record rows (including a per-source host tally); memory and database work grow with case size. This change bounds model context, request/reply sizes and displayed histories, not total forensic workspace size or full-sheet query latency.

API errors: missing case 404; invalid/blank/oversized request or context 422; unavailable model 503; concurrent generation/stale facts 409; timeout 504; malformed/incomplete model reply 502. The existing `X-CDS-Request: local-ui` guard applies. Generation errors release the shared slot. An unsupported question can return a fixed uncertainty message with no generated assertions.

## Saved documents, history and prototype API

The canonical document is a serialized UTF-8 JSON row in `CDS_DATA_DIR/cds.sqlite3`, in `case_briefs`. There is no second filesystem copy to keep synchronized. **Download JSON** returns those exact bytes as a `.json` attachment, with a filename made only from a generated brief ID and version. Reads and exports require no model. Back up the workspace database with the other case data; deleting a case also deletes its owned brief rows, and leaves other cases intact.

Each successful generation receives a UUID and monotonically increasing per-case version. The full computed input is compared again inside the same SQLite write transaction as insertion and audit. Deletion or changed inputs during generation prevents a successful save. There is no update endpoint; a database trigger also prevents updating an existing brief row. The migration creates this table inside the existing migration transaction. Earlier ephemeral responses never had stored rows and cannot be recovered by migration.

Renaming a case, importing a source, reanalysis or changed job state can make a version stale. Staleness is computed at read time against the current full-input digest and lives in the response envelope, outside the immutable document. Historical documents, source/run links and downloads stay unchanged. Stale selected briefs cannot be used for case interpretation in chat: regenerate or select a current version. They remain viewable and downloadable.

This prototype deliberately changes the old `POST /brief` response shape:

| Route | Request / response |
| --- | --- |
| `GET /api/cases/{case_id}/brief` | Deterministic current full fact sheet, input/fact digests and provenance; no AI. |
| `POST /api/cases/{case_id}/brief` | No body. Generate and save; return `{document, stale, document_sha256}` only after commit. Requires `X-CDS-Request: local-ui`. |
| `GET /api/cases/{case_id}/briefs` | Newest-first `[{id, version, generated_at, stale}]`. |
| `GET /api/cases/{case_id}/briefs/{brief_id}` | Owned saved `{document, stale, document_sha256}`; wrong case/ID returns 404. |
| `GET /api/cases/{case_id}/briefs/{brief_id}/download` | Exact stored JSON bytes; attachment and SHA-256 ETag. Wrong case/ID returns 404. |
| `POST /api/cases/{case_id}/chat` | `{mode, message, history?: [{role, content}], facts_digest?: string, brief_id?: string}`; `mode` is `concepts` or `case`. Brief selection is allowed only in case mode, is resolved server-side, and must be current. Chat cannot modify a saved brief. |

The document has `schema_version: "cds.case-assessment.v1"`, `id`, `version`, `case`, `overall_summary`, `observations`, `inferences`, `review_next`, `verification`, `facts`, `model_facts`, `facts_digest`, `input_digest`, `provenance`, `context`, `prompt_version`, `prompt_sha256`, `guidance_version`, `model`, `model_digest`, `runtime_version`, `generated_at`, `duration_ms`, and `generation_options`. Every generated item has a server-assigned `A-<category>-<number>` ID, `text`, supporting `facts` F IDs, and `verification: "unverified"`; inferences additionally have `reasoning`, `alternatives` and `limitations`. Supporting fact snapshots come only from the server, never the model. No numeric confidence scores are requested or accepted. Current prompt versions are `case-assessment.v5` and `learning.v4` (unchanged system guidance pack `0.2`; version change covers the data representation); the saved document schema remains v1.

`input_digest` is SHA-256 of canonical UTF-8 JSON of `{case, sources}` from the input query (sorted keys, compact separators, unescaped Unicode); it excludes itself and generated output. `facts_digest` hashes the complete computed fact array with the same encoding. `document_sha256` is SHA-256 of the stored, sorted-key, two-space-indented JSON including its final newline, and appears only in the envelope/ETag. None is a self-referential hash. Discovery records the installed model digest and runtime version when available, otherwise null. Settings and discovery metadata do not guarantee exact model reproducibility or certify answers.

## Optional real-model evaluation

`scripts/evaluate_local_ai.py` has twelve synthetic development scenarios with independently authored rubrics, spanning saved briefs, case chat, concept chat and selected prior assessment. It includes sparse Registry counts, hostile evidence, false premises, mixed supported/unknown questions and an intentionally wrong authored prior brief. Names and rubrics stay outside model input. These are development checks, not held-out accuracy.

Without `--real-model`, the runner writes a manifest with `not_run` statuses and makes no model calls. With explicit opt-in, it retains raw parsed replies, errors, discovery metadata and timing; all operations carry the exact composed-system version/checksum, including rejected attempts. Human semantic findings remain separate. Use repeatable `--scenario` and `--operation` filters for focused comparisons; an empty selection fails clearly. See [evaluation steps and examples](ai-guidance/evaluation.md#synthetic-runner).

For a no-model manifest, run `.venv/bin/python scripts/evaluate_local_ai.py --scenario sparse_registry --operation case_chat --output /tmp/cds-ai-manifest.json`. Add `--real-model` only for an explicitly intended real-model run. Use a new path outside the repository; reports are never overwritten. The runner does not read evidence or open a case database, and does not replace live saved-brief, startup or UI acceptance.

## Reviewed local lessons and verification

The glossary explains SHA-256 ([NIST FIPS 180-4](https://csrc.nist.gov/pubs/fips/180-4/upd1/final)), deleted entries ([TSK fls](https://www.sleuthkit.org/sleuthkit/man/fls.html)), timestamp kinds/UTC ([Microsoft file times](https://learn.microsoft.com/en-us/windows/win32/sysinfo/file-times)), browser history attribution ([Chrome history](https://support.google.com/chrome/answer/95589?hl=en)), Registry key/value time distinctions ([RegQueryInfoKey](https://learn.microsoft.com/en-us/windows/win32/api/winreg/nf-winreg-regqueryinfokeyw)) and event IDs ([Microsoft event schema](https://learn.microsoft.com/en-us/windows/win32/wes/eventschema-eventid-systempropertiestype-element)). Coverage and saved-run explanations describe CDS behavior; [NIST SP 800-86](https://csrc.nist.gov/pubs/sp/800/86/final) supplies general forensic process background, not certification of CDS.

Run the backend, frontend formatting/build, and Playwright checks listed in README. Tests use synthetic cases and a scripted local HTTP stub with realistic completion metadata. Green tests verify the exercised software behavior, not the truth of model statements. A real Ollama smoke test, runtime version and model-quality/latency review remain separate deployment checks.
